# Lighter as a watchable venue: research (2026-10-22)

*Research output for the on-chain perp DEX expansion (watching public addresses
only, no wallet connects). Not legal advice. Items marked [VERIFY] are
unconfirmed. Live requests were made on 2026-10-22 from a US residential IP
(Champaign, IL; AWS CloudFront POP ORD58), read-only, unauthenticated.
Raw responses are saved under the session scratchpad
`fixtures/lighter/` for the build phase to turn into recorded fixtures.*

## 1. Verdict

**Go with caveats.** Lighter (Elliot Technologies, Inc.; a zk-rollup perp/spot
exchange on Ethereum, mainnet since 2025-01-17) has the best public leaderboard
of any venue checked so far (documented, sortable server-side, four windows,
paged) and, unlike Hyperliquid, its full per-account history is reachable from
public data through the **explorer API** (deep offset paging back to the first
action). The caveats:

1. **Fills over REST are capped.** Unauthenticated `GET /api/v1/trades`
   returns only the **3,000 most recent** trades per account index (confirmed
   live on two accounts: the cursor ends after 30 pages of 100). Deeper
   history must come from the explorer's `accounts/{id}/logs`, which has no
   trade id and uses offset paging.
2. **Funding payments are not public per account.** `positionFunding`
   refuses without auth ("auth required for main accounts"). Funding must be
   *derived* (hourly per-market funding history x position size), or
   cross-checked against `total_funding_paid_out` on open positions.
3. **The docs say `trades` and `pnl` need auth**; the servers do not enforce
   it today. Lighter could close that at any time [VERIFY with Lighter].
4. **Terms exclude US persons from the API itself**, not only the interface
   (stronger than Hyperliquid's wording), and the trading WebSocket rejects US
   IPs. Read-only REST and the `?readonly=true` WebSocket work from the US,
   and Lighter's docs point restricted regions at that read-only socket.
5. **Rate limits are tight without a Builder account**: 60 requests/minute
   per IP on the main API, 90 weight/minute on the explorer.

## 4. Address and account model

- Owner identity is an **Ethereum L1 address** (0x + 40 hex). The API accepts
  any case (`accountsByL1Address` with a lower-cased address returned the same
  account and echoed the lower-case input), so `watchlist.normalize_address`
  and `LeaderboardEntry.address` (lowercased 0x) fit unchanged. Lower-case the
  board's checksummed addresses.
- Trading happens on **account indexes** (integers). One L1 address owns one
  master account (`account_type 0`, small index, e.g. 714710) plus
  sub-accounts (`account_type 1`, index >= 2^48, e.g. 281474976708657).
  Sub-account caps: 4 Standard, 16 Plus, 64 Premium
  (https://apidocs.lighter.xyz/docs/account-types). 11 of the top 15 all-time
  addresses have at least one sub-account.
- Public pools (LLP, staking pool) are also account indexes >= 2^48; an
  address can hold pool **shares** (`shares[]` on `/account`).
- `GET /api/v1/accountsByL1Address?l1_address=` lists every account index of
  an address; `GET /api/v1/account?by=l1_address&value=` returns the master
  account in full (`by=index` for a sub-account).
- **Recommendation:** watch key stays the lower-cased L1 address (what the
  leaderboard and the user paste). The connector enumerates the address's
  account indexes on every sync and treats the address as one Koine account:
  transfers between its own indexes are internal (net zero), transfers to any
  other index are external flows. `account_ref` = the address; per-index
  cursors live inside the composite cursor.
- Lighter on **Robinhood Chain** ("Lighter RH") is a *separate exchange*
  with its own host (`api.rh.lighter.xyz`), chain id 466324, USDG collateral,
  and its own account indexes (https://apidocs.lighter.xyz/docs/lighter-rh).
  Out of scope for v1; if added later it is a second venue (`lighter_rh`),
  not a sub-account.
- No RPC provider is needed: L1 deposits and withdrawals appear as explorer
  log rows (`L1DepositV2`, `WithdrawV2`); Koine never reads Ethereum directly.

### 5.2 Verified-record assessment

- **Fills with stable ids:** REST `trade_id` is stable and unique (3,000 of
  3,000 unique; every tx hash maps to one trade in 1,000 own trades and 100
  BTC market trades). Beyond the newest 3,000 only explorer rows exist,
  keyed by `hash`. One trade per tx hash was observed in every sample, so
  `hash` can serve as `venue_fill_id` for explorer-sourced fills
  [VERIFY: a taker sweep across several makers may log several trades under
  one hash; if so use `hash:ordinal`]. Use one id scheme for both sources:
  `tx_hash` is on REST rows too, so key **all** fills on `tx_hash` and keep
  `trade_id` as metadata.
- **Fees:** never an amount, always a rate integer in **millionths of
  notional** (maker 28 = 0.0028%, taker 196 = 0.0196%, liquidation 10000 =
  1%; matches the Premium fee table). `fee = price x size x rate / 1e6`,
  computed in Decimal and rounded to USDC's 6 dp [VERIFY rounding mode against
  an authenticated export]. Standard accounts pay 0/0. Integrator (partner)
  fees exist (`integrator_*_fee` on `recentTrades`) [VERIFY whether they
  appear on account trades].
- **Every external flow:** yes via explorer logs (deposits, withdrawals,
  transfers to other indexes, pool/staking moves). This is what Hyperliquid
  gives via `userNonFundingLedgerUpdates`.
- **Liquidations:** yes, as fills.
- **Positions + account value for reconcile:** yes.
- **Funding:** derivable, not read directly (above). This is the one place a
  public watch record is computed rather than read; label it in methodology.
- **History depth:** full on the explorer (offset paging; mainnet genesis
  2025-01-17). REST trades: newest 3,000. With a read-only token (`ro:`),
  `export` gives CSVs of up to 12 months of trades / 3 months of funding.
- **Paging hazards:** explorer `offset` counts from the newest row, so new
  activity shifts every offset during a backfill. Walk newest-first, dedupe
  on `hash`, and stop at the last stored hash (resume cursor = newest stored
  hash + time); expect overlap, never gaps. [VERIFY whether `offset` also
  accepts a log/tx id for stable paging; the schema types it as a string.]
- **Cost:** a 200,000-row account is 2,000 explorer pages = ~45 minutes at 90
  weight/min (weight 2). Daily syncs are a handful of pages. Backfills must be
  queued and throttled per IP like Hyperliquid's.

**Answer: yes, a full verified track record is rebuildable from public data
alone**, with funding derived, explorer-sourced fills keyed by tx hash, and a
dependency on two undocumented-in-practice behaviours (unauthenticated
`trades`/`pnl`; explorer depth). A creator who connects a read-only token
(`ro:{account_index}:all:{expiry}:{hex}`, "can never trade", 1 day to 10
years) would get the authoritative endpoints (`positionFunding`,
`deposit/history`, `transfer/history`, `withdraw/history`, `liquidations`,
`export`): https://apidocs.lighter.xyz/docs/api-keys#read-only-authentication .
That is a natural later creator-connect path (`CredentialKind` token,
`ReadOnlyProof` by construction).

## 10. Fit with contract v2 vs Hyperliquid

Maps directly:
- `AssetVenueConnector` + `AssetMarketData`; `OwnershipProof` public address;
  `credential` none; `quote_asset` "USDC"; `InstrumentType` perp + spot;
  `NormalizedInstrument` from `orderBookDetails` (decimals <= 6, well under 12).
- `NormalizedAssetFill` from REST trades or explorer trade pubdata: action
  from `is_maker_ask` + which side the account is on; legs = realized/margin
  USDC leg + fee leg (fee computed from rate) as the Hyperliquid connector
  does. Spot fills (LIT/USDC) are two-asset like Hyperliquid spot.
- `NormalizedEvent`s for deposits, withdrawals, transfers (`venue_ref` =
  tx hash), liquidations as fills.
- `fetch_balances`: `/account` `total_asset_value` + `assets[]` per index,
  summed per address; positions with `avg_entry_price`.
- `fetch_leaderboards` returns all four periods; easier than Hyperliquid
  (server-side sort, no 38 MB parse).
- `StreamMode.FILLS` via `account_all_trades`.

New or awkward:
1. **Composite account:** one watched address = N account indexes discovered
   at sync time. Hyperliquid has one address = one account (subaccounts are
   separate addresses there). Needs per-index cursors inside one
   `Page` cursor and an "internal transfer" rule (own index to own index).
2. **Two sources for fills with a seam at 3,000:** REST for the live edge
   (rich fields, trade id), explorer for backfill. Same `venue_fill_id`
   (tx hash) on both or idempotency breaks.
3. **Derived funding:** a computed event kind (`ref_is_content_hash=True`
   style id, e.g. `funding:{index}:{market}:{hour}`), new for Koine; must be
   documented in methodology as computed from Lighter's published hourly
   rates.
4. **Fees as rates:** fee amount computed from price x size x rate/1e6, the
   only venue where Koine computes the fee.
5. **Pool shares and staking** (LLP, LIT staking) are holdings without a
   quote in `prices`; v1 can flag them as unsupported activity
   (`activity_flags`) and exclude such addresses from discover, or value
   shares from pool metadata [VERIFY].
6. **Floats in JSON** on leaderboard/pnl (strings on trades/account). Parse
   with `parse_float=Decimal` throughout.
7. **Synthetic equities / FX / pre-IPO perps** and binary options on the same
   venue: `asset_classes` crypto plus "equities-like" perps; binary options
   flagged unsupported.
8. **Address normalization:** no change (0x + 40 hex, case-insensitive), so no
   shared non-0x work. No chain id in Koine's model (Lighter mainnet only;
   RH would be a separate venue). **No RPC provider.**
9. **Two rate-limit scopes** per IP (`api`, `explorer`); both are small.

Effort: **L.** Connector (two fill sources, composite account, explorer
event parsing, funding derivation, fee computation) ~1.5x Hyperliquid's;
leaderboard fetcher S; stream mode S; profile, terms doc
(`docs/venues/lighter.md` incl. Watchlist and Leaderboard sections), consent
text and fixtures M. Funding derivation needs hand-computed unit tests.

## 11. Risks

- Lighter enforces the documented auth on `trades`/`pnl` (then only the
  explorer remains, and the live edge must come from the WS or explorer).
- Explorer is an operational surface (`explorer.elliot.ai`), not the
  versioned API; schema drift (`L1Deposit` -> `L1DepositV2` already happened)
  and offset-paging instability.
- Funding derivation mismatches Lighter's settlement (rounding, discounts:
  `funding_fee_discounts_enabled`, `discount` in PositionFunding) -> reconcile
  drift on `total_asset_value`.
- Terms name the API and exclude US entities; counsel and a Lighter contact
  needed. Datacenter (Fly) IPs could be blocked harder than residential.
- 60 req/min IP budget: backfills of very active addresses take tens of
  minutes; discover refresh competes with syncs. Builder account may be
  needed and may be refused to a US applicant.
- Leaderboard semantics (roi denominator, pool-share inclusion, sub-account
  aggregation) unconfirmed; labelled as Lighter's own numbers anyway.
