# dYdX v4 (dYdX Chain) as a watchable venue: research (2026-10-22)

*For the copy strategies track (watchlist + discover, paper only). Compiled
from live requests made from a US residential IP (Champaign, IL, AS23473) on
2026-10-22, the open-source indexer in `dydxprotocol/v4-chain`
(`indexer/services/comlink`, `socks`, `packages/compliance`, `packages/postgres`
on `main`), the official docs at docs.dydx.xyz, and the dYdX Software Terms of
Use. Not legal advice. **[VERIFY]** = not confirmed by a live response or a
primary source. Raw responses are saved for the build phase under the session
scratchpad `fixtures/dydx/` (list in section 10).*

---

## 0. Verdict in five lines

1. **No-go from US egress as things stand.** Every per-address indexer
   endpoint (`/addresses`, `/fills`, `/transfers`, `/fundingPayments`,
   `/perpetualPositions`, `/historical-pnl`, `/pnl`, `/tradeHistory`,
   `/orders`, `/assetPositions`) returns **HTTP 403 `GEOBLOCKED`** to a US IP.
   This is deliberate, not a side effect: the code (`complianceAndGeoCheck`)
   blocks any request whose Cloudflare `geo-origin-status` is not `ok`, and
   Fly `iad` is US. Prod Koine could not read one fill.
2. **The data itself would fit Koine well.** Outside the block, the indexer
   serves everything the pipeline needs: fills with stable ids, fees,
   liquidation types, per-position funding payments, every
   deposit/withdrawal/subaccount transfer, positions and equity, and full
   history via height cursors (no Hyperliquid-style 10k cap).
3. **There is no public leaderboard.** The indexer has no ranking endpoint
   and the official front end (dydx.trade) calls none. Discover would have
   nothing to read.
4. **The terms are stricter than Hyperliquid's.** They bar anyone
   "operated or controlled from the United States" from the perpetuals
   software, ban VPN circumvention, and bar modifying the software to
   impair Restricted-Person detection. Routing around the block (non-US proxy,
   or self-hosting the indexer with geoblocking off) is exactly what they
   forbid.
5. **The venue is small now.** Measured 24h volume on 2026-10-22: ETH-USD
   $27.5M, BTC-USD $6.9M, SOL-USD $2.5M; 73 of 296 markets ACTIVE. Even if
   reachable, there are few traders worth copying. **Recommendation: no-go;
   revisit only if dYdX opens perpetuals to US persons.**

## 1. Geoblocking (tested live)

Every response carries `geo-origin-country: US`, `geo-origin-region: US-IL`,
`geo-origin-status: restricted` (Cloudflare in front of an Express app).

| Request | Result |
|---|---|
| `GET /v4/time`, `/v4/height`, `/v4/perpetualMarkets`, `/v4/orderbooks/perpetualMarket/BTC-USD`, `/v4/historicalFunding/BTC-USD`, `/v4/trades/...`, `/v4/candles/...`, `/v4/sparklines`, `/v4/affiliates/snapshot`, `/v4/vault/v1/megavault/*`, `/v4/compliance/screen/{addr}`, `/v4/trader/search` | 200 |
| `GET /v4/addresses/{addr}`, `/addresses/{addr}/subaccountNumber/0`, `/fills`, `/transfers`, `/fundingPayments`, `/perpetualPositions`, `/historical-pnl`, `/pnl`, `/tradeHistory`, `/orders`, `/assetPositions` | **403** `{"errors":[{"code":"GEOBLOCKED","msg":"Because you appear to be a resident of, or trading from, a jurisdiction that violates our terms of use ..."}]}` |
| `GET https://api.dydx.exchange/v4/geo` | `{"geo":{"country":"US",...,"blocked":true}}` |
| `wss://indexer.dydx.trade/v4/ws`, subscribe `v4_subaccounts` `{addr}/0` | `subscribed` with a subaccount snapshot (equity, positions). **Not blocked**, see below |
| Public full-node REST (Polkachu, KingNodes, publicnode): `/dydxprotocol/subaccounts/subaccount/{owner}/{n}`, `/perpetuals/perpetual`, `/v4/feetiers/perpetual_fee_params`, `/clob/clob_pair` | 200 |

The code path. `indexer/services/comlink/src/lib/compliance-and-geo-check.ts`
lets a request through only if the caller is an internal indexer IP, the
address is on the operator's `WHITELISTED_ADDRESSES`, or the address has
compliance status `CLOSE_ONLY`/`FIRST_STRIKE_CLOSE_ONLY`. Otherwise
`isRestrictedCountryHeaders` (`packages/compliance/src/geoblocking/util.ts`)
returns true whenever `geo-origin-status !== "ok"`, and the endpoint answers
403. Every address route in comlink applies this middleware. The switch is
`INDEXER_LEVEL_GEOBLOCKING_ENABLED`, an operator setting.

Websocket gap. The socks service forwards the client's geo headers to the
same comlink endpoints for a subscription's initial snapshot
(`services/socks/src/lib/subscription.ts`
`getInitialResponseForSubaccountSubscription`, which throws `BlockedError`
on a 403). The live subscription still succeeded from a US IP, so those
headers apparently did not reach comlink on the websocket path. **Treat
this as an enforcement gap that could close at any time, not as
permission.** Building on it knowingly would be circumvention in spirit
(section 6). [VERIFY why it passed; the address tested had zero equity,
but REST for the same address was 403, so CLOSE_ONLY status is not the
explanation.]

Workarounds, and why each fails:

- **Non-US egress (proxy/VPN, a Fly region outside the US).** Explicitly
  prohibited ("Use of any technology or mechanism, such as a virtual private
  network ('VPN') to circumvent the restrictions set forth herein is
  prohibited"). Koine is US-controlled, so a non-US machine does not change
  who is accessing.
- **Self-host the indexer** (open source; full node + Postgres + Kafka +
  Redis + ender/roundtable/comlink/socks/vulcan, replayed from genesis
  2023-10, about 110.6M blocks). XL operational cost, and the terms forbid
  modifying dYdX Software in a way "that impairs the default detection and
  prevention mechanisms with respect to Restricted Persons". [VERIFY with
  counsel whether running it unmodified with geoblocking simply not
  configured counts.]
- **Public full nodes / archive nodes** (docs list Polkachu 300 req/min,
  KingNodes 350 req/min, Enigma; reachable from the US). They serve **current
  state only**: subaccount asset/perp positions in quantums, market params,
  fee tiers. Fills, funding payments and transfers are block events, not
  state; rebuilding them means decoding every block's events from an archive
  RPC (`block_results`) for the chain's whole history. That is an on-chain
  indexer project, and the same terms question applies.
- **Third-party data vendors** (Numia, Allium, others) may sell indexed dYdX
  data [VERIFY: none confirmed]. Their licences, and whether they serve US
  customers, are unknown.

historical-block-trading-rewards, historical-funding, historical-pnl,
historical-trading-reward-aggregations, orderbook, orders,

dydx.trade bundle (`/assets/main-C4a5wKE5.js`, 9.3 MB) contains no
leaderboard URL.

Near misses, none usable:

- `/v4/affiliates/snapshot`: addresses ranked by **affiliate earnings and
  referred volume**, with a referral code (a name-like handle). Not trading
  performance.
- `/v4/historicalTradingRewardAggregations/{address}`: per address, and
  geoblocked.
- `/v4/trader/search?searchParam=`: maps an address to an auto-assigned
  `username` (for example "OtherBrief3BK"). An identity-like handle that Koine
  must never store or show.
- Third-party boards (for example dydx.daic.capital, "updated every 2hrs")
  are scraped sites with no API and unknown provenance [VERIFY]. Ranking them
  ourselves would need per-address data, which is blocked.

`VenueProfile.leaderboard_periods` would be `()`, and
`fetch_leaderboards` would return `{}`.

| Equity series | `/v4/historical-pnl` (hourly/daily ticks), `/v4/pnl?daily=` | `equity`, `totalPnl`, `netTransfers` (a ready cross-check for TWR) |

IDs. Fill ids are `uuid(eventId-hex + "-" + liquidity)` and transfer ids are
`uuid(eventId, assetId, sender, recipient ...)`, where eventId encodes block
height plus transaction and event index (`packages/postgres/src/stores/fill-table.ts`,
`transfer-table.ts`). They are deterministic from chain data, so they are
stable across re-indexing. Good for append-only idempotency.

Paging and depth. `limit` defaults to and caps at `API_LIMIT_V4 = 1000`.
`page` is offset paging, capped by `MAX_PAGINATION_OFFSET = 25,000` (added
after a "2026-07-11 weekend paging incident", per the config comment), so
offset paging reaches about 26k rows at most. A full backfill must instead
walk `createdBeforeOrAtHeight` downwards (keyset by height). Funding pages
forward with `afterOrAt` + `page`. The indexer keeps history since mainnet
genesis (October 2023) [VERIFY no pruning on the public instance]. That would
mean **`history_depth="all"`**, better than Hyperliquid.

External flows. DEPOSIT / WITHDRAWAL (bridge or wallet to subaccount) and
TRANSFER_IN / TRANSFER_OUT (between subaccounts or addresses) are all
indexed, so `transfers_observable=True`. Trading rewards (DYDX) go to the
wallet, not the subaccount, and do not touch equity.

Rate limits (comlink defaults, `config.ts`, per IP): GET 100 per 10 s
(observed live: `ratelimit-limit: 100`), fills 100 per 10 s, funding 100 per
10 s, pnl 100 per 10 s, candles 1000 per 10 s. Websocket: 2 subscribes/s;
256 `v4_subaccounts` and 256 `v4_parent_subaccounts` channels per connection.
There is no documented per-IP user cap like Hyperliquid's 10.

## 4. Market data (public, not geoblocked)

- **Instruments**: `GET /v4/perpetualMarkets` (296 markets, 73 ACTIVE). Each
  has `ticker` ("BTC-USD"), `tickSize` ("1"), `stepSize` ("0.0001"),
  `atomicResolution` (-10), `quantumConversionExponent`, `subticksPerTick`,
  `stepBaseQuantums`, margin fractions, `marketType` CROSS/ISOLATED,
  `oraclePrice`, `nextFundingRate`. qty decimals = -log10(stepSize); USDC has
  6 decimals (asset id 0, quantums at 1e-6).
- **Quotes**: `GET /v4/orderbooks/perpetualMarket/{ticker}` gives full bids
  and asks (up to 100 levels a side), for example best bid 81372 / ask 81393
  on BTC-USD. The ws `v4_orderbook` channel streams batched deltas. Spreads are
  wide on most markets.
- **Funding**: hourly. `GET /v4/historicalFunding/{ticker}` gives
  `rate`, `price`, `effectiveAt`, `effectiveAtHeight` (BTC 17:00Z rate
  0.000006375).
- **Daily closes**: `GET /v4/candles/perpetualMarkets/{ticker}?resolution=1DAY`.
- **Fees** (chain state, `/dydxprotocol/v4/feetiers/perpetual_fee_params`):
  tier 1 taker 500 ppm = **5.0 bps**, maker 100 ppm = 1 bp; tier 2 taker
  4.5 bps. So `fee_rate_bps=5`, the same as Hyperliquid's rounded value.
  Fees print 6 dp USDC.

## 5. Address and subaccount model

- **Address**: Cosmos bech32, `dydx1` + 38 chars (20-byte account,
  secp256k1). It is derived deterministically from a signature by the user's
  Ethereum (or Solana, or passkey/Turnkey) wallet, so **there is no
  computable mapping between a dydx1 address and an 0x address.** Normalize
  by lowercasing (bech32 forbids mixed case) and validating the checksum.
- **Subaccounts**: numbers 0..128,000. Numbers 0-127 are "parent"
  subaccounts (cross margin). Isolated-margin positions live in child
  subaccounts `n` with `n % 128 == parent` (128, 256, ...). The
  `parentSubaccountNumber` endpoints aggregate a parent and its children.
  Moving collateral to a child is a TRANSFER_OUT/IN between the address's own
  subaccounts [VERIFY whether the parent-level transfer endpoint nets these
  out].
- **What a watched account should key on**: `(dydx1 address, parent
  subaccount 0)`, read through the parent-subaccount endpoints, so isolated
  positions are included. In practice almost every trader uses parent 0 only
  [VERIFY]. Store it as `account_ref="dydx1...:0"`, or the address alone with
  subaccount 0 implied.
- **Opt-out / claim proof**: EIP-191 does not apply. The owner would sign an
  ADR-036 `signArbitrary` message (Keplr/Leap/Cosmos wallets; the dydx.trade
  key is derived in-browser and not exported to such a wallet [VERIFY]).
  Verifying that is a secp256k1 + bech32 check, new code next to
  `hyperliquid.recover_signer`. Many dYdX users never hold the raw key, so a
  manual opt-out route is needed anyway.
- **Chain**: `dydx-mainnet-1`, one chain, USDC only collateral.

say nothing about the info API, and do not enforce a block on reads. dYdX's

Hyperliquid because reading was not actually blocked. Here the only way to
read is to get around a control aimed at exactly this, so **this one is a
real no-go for a US company**, unless counsel says otherwise.

perpetuals remain unavailable to US persons (The Block,

If perpetuals ever open to the US, the indexer geoblock would presumably
lift, and this note becomes a go-with-caveats build.

## 7. Fit with contract v2 (if the block ever lifts)

Maps directly:

- `AssetVenueConnector` + `AssetMarketData`, `CredentialKind.ADDRESS`,
  `ReadOnlyProof.NONE`, `InstrumentKind.ASSET`, `PaperFeeModel.BPS_OF_NOTIONAL`,
  `quote_asset="USDC"`, `transfers_observable=True`, `history_depth="all"`.
- Fills → `NormalizedAssetFill`: perp "<COIN>-PERP" FILL_BASE legs, a FEE leg
  (sign flip; rebates positive), REALIZED_PNL derivable from
  `positionSizeBefore`/`entryPriceBefore` (dYdX does not print closedPnl per
  fill; compute it, as Hyperliquid does not need to) [VERIFY the fields are
  populated for old fills]. `liquidity` maker/taker. Builder and router fees
  are separate fields to fold into FEE.
- Funding → `NormalizedEvent(kind=FUNDING)` with a synthetic ref.
- Transfers → DEPOSIT/WITHDRAWAL/TRANSFER_IN/TRANSFER_OUT events, with
  internal parent/child moves dropped or netted.
- Balances → `NormalizedBalances` from the subaccount: USDC asset position
  (cash excluding unrealized P&L, as the contract wants) + perp entries with
  `entry_price`; `equity_usd_micros` = `equity`.
- `Page` cursors: keyset on `createdBeforeOrAtHeight` (one request per page);
  `resume_cursor` = last seen height per stream (fills, transfers, funding).
- `fetch_quote` from the orderbook, `fetch_funding_history`,
  `fetch_daily_closes` from candles, `fetch_instruments`, `fetch_margin_tiers`
  from IMF/MMF (no tier table; single fraction plus OI caps).
- Streaming: `v4_subaccounts` / `v4_parent_subaccounts` push fills, transfers
  and positions per block → `StreamMode.FILLS`, `stream_users_per_ip=None`
  (256 channels per connection).

New shared work it would force:

1. **Non-0x addresses.** `watchlist.ADDRESS_RE`/`normalize_address`,
   `LeaderboardEntry.address` ("lowercased 0x address"),
   `hyperliquid.is_address`, the watch form's "Enter a 0x address" error, and
   `watch_optouts` all assume 0x+40hex. Needs a per-venue address validator in
   the profile (for example `VenueProfile.address_kind` = "evm" | "bech32:dydx"
   | "solana") with bech32 checksum validation (add a tiny `bech32` dependency
   or vendor the 60-line reference implementation).
2. **A Cosmos signed opt-out** (ADR-036 verification) next to EIP-191.
3. **Subaccount in the account key.** `account_ref` must carry the parent
   subaccount, and transfers must net parent<->child moves.
4. **Quantum/subtick math is not needed** if only indexer decimal strings are
   used (they are human units). It would be needed for node-state
   reconciliation (`quantums`, `atomicResolution`).
5. **No RPC dependency through the indexer.** The RPC/archive-node route is
   only a fallback, and it means a real chain indexer.
6. **Geo-aware egress.** The real blocker, and not something Koine should
   build (section 1).
