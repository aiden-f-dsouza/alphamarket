## 0. Verdict in five lines

1. **Reachable from the US.** Every public surface (GMX API, Oracle API,
   Subsquid GraphQL, both peers and fallbacks, Arbitrum and Avalanche)
   answered 200 to a US IP, with no geo header checks and no 429 in a
   40-request burst. Only the *Interface* terms exclude US persons.
2. **There is a real public leaderboard**: `accountPnlRankMetrics` in the
   official GraphQL, per address, periods `today`, `yesterday`, `week` (rolling
   7 d), `month` (rolling 30 d), `year` (calendar), `all`, with PnL (USD),
   PnL bps on max capital, volume and max capital. Refreshed in place (one
   window per period, `updatedAt` minutes old). Addresses only, no names.
3. **Fills are excellent**: every executed order is a `TradeAction` with a
   stable id `txHash:logIndex`, execution price, size in USD and tokens, the
   position, borrowing and funding fees paid, liquidation fee, price impact
   and realized PnL, full history back to GMX v2 launch (2023-07-13), from
   both the GMX API (`GET /trades`) and the GraphQL.
4. **The hard part is equity, not data.** GMX v2 has no venue account
   balance: each position carries its own collateral from the wallet, and
   funding received becomes a claimable balance in several tokens. Koine's
   flow-adjusted TWR assumes a venue-held balance with deposits and
   withdrawals. For GMX, Koine would have to build a synthetic "margin account":
   collateral in at each increase, payouts at each decrease, claimables, and
   the optional GMX Account balance. Equity is zero whenever the trader is
   flat. This is new shared methodology work, and it is the main cost.
5. **Recommendation: go with caveats**, Arbitrum only first. The data is
   public, deep, unblocked and has stable ids. Budget an L: a GraphQL
   client, a position-scoped instrument model (market + collateral + side,
   hedged long and short at once), a 30-decimal fixed-point layer,
   checksum handling, and a methodology section for an account with no
   balance. No RPC provider is needed for v1; a websocket is optional (none
   is public).

## 2. Public leaderboard (discover)

**Endpoint:** GraphQL `accountPnlRankMetrics` (entity `AccountPnlRankMetric`).
No auth. Offset/limit paging (`limit: 1000` returned 104 KB in 0.5 s).

```graphql
{ accountPnlRankMetrics(limit: 100, offset: 0, orderBy: pnlUsd_DESC,
                        where: { period_eq: "month" }) {
    id account period fromTimestamp volume maxCapital pnlUsd pnlBps updatedAt } }
```

| Field | Meaning (observed) |
|---|---|
| `id` | `period:fromTimestamp:account` |
| `account` | EIP-55 checksummed address (mixed case) |
| `period` | `today`, `yesterday`, `week`, `month`, `year`, `all` (other strings return 0 rows) |
| `fromTimestamp` | window start: today = 00:00 UTC today, week = now − 7 d at 00:00 (2026-10-15), month = − 30 d (2026-09-22), year = 2026-01-01, all = 0 |
| `pnlUsd` | 30-decimal USD integer string |
| `pnlBps` | PnL / max capital, basis points (11138 = 111.38%) |
| `volume`, `maxCapital` | 30-decimal USD |
| `updatedAt` | unix s; all rows minutes old on 2026-10-22 17:20 UTC |

Row counts on Arbitrum at fetch time: today 2,174, week 2,575, month 3,313,
year 11,954, all 181,201. Each period holds exactly one window (all rows of a
period share `fromTimestamp`), so no window filter is needed. Ordering by
`pnlUsd_DESC` or `pnlBps_DESC` both work (the app's leaderboard also applies a
min-capital filter, as `accountPnlSummaryStats(account, rankMaxCapitalGte)`
does; [VERIFY] the exact threshold the app uses).

Whether `pnlUsd` includes unrealized PnL: the per-account resolver
`accountPnlSummaryStats` returns `pnlUsd = realized + unrealized −
startUnrealized` per bucket (`today`, `yesterday`, `week`, `month`, `year`,
`all`) with `usedCapitalUsd`, `wins`, `losses`, fee breakdowns and ranks.
The ranking metric most likely uses the same definition. [VERIFY]

Mapping to `LeaderboardPeriod`: DAY → `today` (or `yesterday` for a
complete day), WEEK → `week`, MONTH → `month`, ALL → `all`. `LeaderboardEntry`:
`address = account.lower()`, `pnl = pnlUsd / 1e30`, `roi = pnlBps / 10000`
(note: the denominator is *max capital used*, not account value; label it so),
`volume = volume / 1e30`, `account_value = None` (GMX publishes no account
value; `maxCapital` is not the same thing). One call per period; the
Avalanche squid has the same resolver (`avax_squid_rank_month.json`).

There is **no leaderboard endpoint on the GMX API** (REST). `GET
/performance/snapshots|annualized?address=` is GM/GLV *pool* performance, not
traders (returned `[]` for a trader).

## 3. Per-address history

### 3.1 Fills (trade actions)

Two equivalent sources; the REST API looks like a proxy over the indexer
(same ids and fields).

**GMX API `GET /trades`**: `address` (lowercase accepted), `symbol`,
`marketAddress`, `since`, `until` (unix seconds, inclusive), `actions[]`,
`limit` (1..300, error text "limit must be between 1 and 300"), `cursor`.
Response `{trades, nextCursor, hasMore}`, newest first.
**Gotcha (confirmed live): the cursor is a plain offset and stops at 10,000.**
Any `cursor >= 10000` returns the rows at offset 10,000 again with
`nextCursor: "10003"`, so naive cursor paging loops and duplicates (18,300
rows, 10,300 unique on a 56k-row address). Page by time instead: `until =
oldest timestamp seen`, dedupe by `id` (rows in the boundary second repeat).
`until=1700000000` (before v2 launched) returns HTTP 500.

**GraphQL `tradeActions`**: `where: {account_eq: <checksummed>, eventName_eq:
"OrderExecuted"}`, `orderBy: [timestamp_ASC, id_ASC]`, keyset by
`timestamp_gte` + id. **`account_eq` is case-sensitive**: the lowercase
address returned 0 rows, the checksummed one returned them. Koine must
EIP-55 checksum (keccak) before querying; storing lowercase is fine.

Fields per row (observed): `id` (`txHash:logIndex`, stable and unique),
`eventName` (`OrderCreated`, `OrderExecuted`, `OrderCancelled`, `OrderFrozen`
[VERIFY]), `orderType` (0 MarketSwap, 1 LimitSwap, 2 MarketIncrease, 3
LimitIncrease, 4 MarketDecrease, 5 LimitDecrease, 6 StopLossDecrease, 7
Liquidation, 8 StopIncrease [VERIFY numbering against contracts `Order.sol`]),
`orderKey`, `account`, `marketAddress`, `isLong`,
`initialCollateralTokenAddress`, `initialCollateralDeltaAmount`,
`sizeDeltaUsd`, `sizeDeltaInTokens`, `executionPrice`, `indexTokenPriceMin/Max`,
`collateralTokenPriceMin/Max`, `priceImpactUsd`, `totalImpactUsd`,
`positionFeeAmount`, `borrowingFeeAmount`, `fundingFeeAmount`,
`liquidationFeeAmount`, `traderDiscountAmount`, `uiFeeReceiver`/`uiFeeFactor`,
`pnlUsd`, `basePnlUsd`, `collateralTotalCostAmount`, `executionAmountOut`,
`timestamp`, `transactionHash`; GraphQL-only: `positionKey`,
`positionLifecycleId` (added 2026-06-30, backfilled 2026-10-08),
`positionSizeInUsd/InTokens` (after the change), `isFundingFeeSettle` (from
2026-08-18).

Decoded example (fixture `arb_api_trades_page1.json`, first row, XPL/USD
short close): `sizeDeltaUsd` 106,125.23 (entry notional; GMX `sizeInUsd` is
fixed at entry), `sizeDeltaInTokens` 690,631.53 XPL, `executionPrice`
79827656320 → 0.0798 USD (price × 10^(18−30) for an 18-decimal token),
`basePnlUsd` 51,033.09, `pnlUsd` 45,811.06, fees in USDC (6 dec): position
63.68, borrowing 3,646.51, funding 1,594.95.

Conventions Koine must implement: USD values are 30-decimal integers;
a token price is scaled by 10^(30 − token decimals); token amounts use the
token's own decimals (USDC 6, WBTC 8, WETH 18, SOL 9); fees are in the
*collateral token*, not USD. Index tokens can be synthetic (XPL on Arbitrum
has an address and 18 decimals but no ERC-20), so the instrument is the
market, not a token.

Depth: full history back to GMX v2 launch. The oldest Arbitrum trade action is
2023-07-13 (`timestamp 1689269817`). The top address has 56,819 trade-action
rows since 2024-11-12, all served. **No Hyperliquid-style 10k cap** (only the
REST offset cap above).

### 3.2 Funding and borrowing

GMX v2 has no periodic funding payments. Funding and borrowing accrue
per position and **settle on the next position change**:
- **Paid** funding and borrowing are deducted from collateral and reported on
  the executing trade action (`fundingFeeAmount`, `borrowingFeeAmount`, in the
  collateral token). Since 2026-08 a keeper can also settle funding without a
  trade (`isFundingFeeSettle = true` trade actions; claim actions
  `SettleFundingFeeCreated/Executed`). These show as `positionChanges` with
  `sizeDeltaUsd = 0`, `feesAmount > 0`.
- **Received** funding is credited to a *claimable* balance per (market,
  token), possibly in the long token (WETH, WBTC, ARB, ...) rather than USDC.
  The trader later claims it to the wallet: `claimActions` with `eventName:
  "ClaimFunding"`, parallel arrays `marketAddresses`, `tokenAddresses`,
  `amounts`, `tokenPrices`; id `txHash:account:ClaimFunding`. Pending
  claimables appear per position in `GET /positions` (`claimableLongTokenAmount`,
  `claimableShortTokenAmount`, `pendingClaimableFundingFeesUsd`), and the
  GraphQL has `claimableFundingFeeInfos` and `AccountStat.positiveFundingFeesUsd`
  (docs 2026-07-21: "the signed PnL contribution from funding received
  through ClaimableFundingUpdated, whether claimed or not").
- Accrual between changes is not an event. Koine either ignores it until
  settlement, which is correct for the ledger, or marks it as unrealized,
  using `pendingFundingFeesUsd` and `pendingBorrowingFeesUsd` from `/positions`.

Borrowing fees are a new cost type. Hyperliquid has funding only.

### 3.3 Deposits, withdrawals, transfers: the core mismatch

Two funding modes coexist, and positions belong to the wallet in both
(docs "Wallet funds and GMX Account funds"):

1. **Wallet mode (classic, the majority) [VERIFY share]:** no venue balance
   exists. An increase order pulls `initialCollateralDeltaAmount` of a token
   from the wallet (optionally swapped through `swapPath`). A decrease sends
   collateral plus or minus PnL, minus fees, back to the wallet. The PnL can
   come in a second token (for example a long ETH profit paid in WETH while
   the collateral is USDC). The trade action gives the inputs
   (`initialCollateralDeltaAmount`, `basePnlUsd`, fees, `collateralTotalCostAmount`,
   `executionAmountOut` for swaps) but **no single "amount sent to wallet" per
   token**. [VERIFY: whether the PositionDecrease event's `outputAmount` and
   `secondaryOutputAmount` are exposed anywhere public. They are not in the
   `TradeAction` or `PositionChange` schemas as introspected.]
   `positionChanges` does carry the **running collateral of the position
   after each change** (`collateralAmount`) and `collateralDeltaAmount`. That is
   enough to replay and reconcile each position's collateral leg exactly.
2. **GMX Account (multichain, Arbitrum settlement only):** a real trading
   balance held in GMX's MultichainVault. Its flows are public in the GraphQL:
   `multichainSamechainFundingEvents` (`operation: deposit|withdrawal`,
   `token`, `amount`, `txHash`, `timestamp`), `multichainFundingSendEvents` /
   `multichainFundingReceiveEvents` and the resolver
   `multichainFunding(where: {account})` (source chain, sent, received,
   executed tx). **No public endpoint returns the current GMX Account
   balance**: `/balances/wallet` is the plain wallet. Replay the flows plus
   trades, or read DataStore over RPC. [VERIFY]

What this means for Koine's TWR: a GMX "account" is a set of positions plus
claimables plus an optional GMX Account balance. Koine would model it as a
synthetic margin account whose external flows are: collateral posted (in) at
each increase; payouts (out) at each decrease or liquidation remainder; claimed
funding (out); and GMX Account deposits and withdrawals. Equity is the sum of
position `netValue`, unclaimed funding and the GMX Account balance. Equity is
**exactly zero whenever the trader is flat in wallet mode**, so the TWR chain
has holes. Methodology must say how they are bridged (skip flat sub-periods)
and must not divide by zero. GMX itself sidesteps this by ranking on
`pnl / maxCapital`. This is the largest piece of new shared work (section 9).

Hyperliquid, by contrast: one USDC account, `userNonFundingLedgerUpdates` lists
every deposit, withdrawal and transfer, and `accountValue` reconciles it. dYdX
is the same with subaccount transfers.

### 3.5 Current positions and value (reconcile)

`GET /positions?address=` (fixture `arb_api_positions.json`) returns per open
position: `key` = `account:market:collateralToken:isLong` (and `contractKey`,
the on-chain bytes32), `sizeInUsd`, `sizeInTokens`, `collateralAmount`,
`entryPrice`, `markPrice`, `liquidationPrice`, `pnl`, `pnlAfterFees`,
`netValue`, `netValueAfterAllFees`, `pendingBorrowingFeesUsd`,
`pendingFundingFeesUsd`, `pendingClaimableFundingFeesUsd`,
`claimableLong/ShortTokenAmount`, `leverage`, `increasedAtTime`,
`decreasedAtTime`. GraphQL `positions` (filter `isSnapshot_eq: false`,
`sizeInUsd_gt: "0"`) has the indexer's view with `realizedPnl`,
`unrealizedPnl` and `openedAt`.

Reconcile = replayed collateral per position (from `positionChanges`)
equals `collateralAmount` from `/positions`, plus replayed claimables equal
to the claimable amounts. There is no account-level balance to check outside
GMX Account users.

### 3.6 Ids and gaps

- Trade action id `txHash:logIndex` is unique and stable (confirmed across REST
  and GraphQL). Claim action id `txHash:account:eventName`.
- **`PositionChange.id` is the bare tx hash** (observed); two changes in one
  tx would collide [VERIFY whether the indexer suffixes]. Use trade actions as
  the fill source and position changes only for reconciliation.
- One transaction can hold several orders (TWAP parts, TP/SL), so the tx hash
  alone is not a fill id.
- Indexer lag: `processorStatuses` showed ~1 s behind the chain head. The
  docs warn that GraphQL is "indexed data. Expect lag relative to live chain
  state."
- Chains other than Arbitrum are separate indexers. The same address can
  trade on Arbitrum and Avalanche (`0xE8d8...91db` ranks on both).

## 4. Market data for paper fills

- **Instruments:** `GET /markets` (Oracle and GMX API): `name` like
  `"ETH/USD [WETH-USDC]"`, `marketToken` (the market id), `indexToken`,
  `longToken`, `shortToken`, `isListed`, `listingDate`. 131 markets on Arbitrum,
  including TradFi (gold, oil, SPY, QQQ). Several markets share an index (ETH/USD
  has WETH-USDC, USDG-USDG and single-token pools), so **the instrument is the
  market address, not the symbol**. `GET /tokens` gives symbol, address,
  decimals and `synthetic`.
- **Tick/step:** none. GMX executes at oracle prices with arbitrary precision.
  Sizes are USD amounts with 30 decimals, and there is no lot size. The
  practical limits are a minimum position size and minimum collateral
  (`minCollateralFactor` 0.5%–1% → max leverage) [VERIFY the min collateral
  USD on-chain setting]. Koine's `tick_micros` / `contract_step_micros` would
  be nominal (for example 1 micro) and quantity atoms use the index token's
  decimals.
- **Bid/ask:** there is no order book. `GET /prices/tickers` (Oracle, 1 s
  backend cache) returns per token `minPrice` and `maxPrice` (signed oracle
  range), and `GET /markets/tickers` (GMX API) returns per market `minPrice`,
  `maxPrice`, `markPrice`, 24 h OHLC, OI and the rates. GMX fills long-opens and
  short-closes at the max price and short-opens and long-closes at the min price,
  **plus a size-dependent price impact** (`positionImpactFactor*`,
  `positionImpactExponentFactor*` in `/markets/config`). The fixture showed
  min = max for ETH at that instant. A paper fill should use the max or min
  price as the "ask" or "bid" and either ignore impact (as a documented
  optimism) or compute it with the GMX formula [VERIFY formula in
  docs "Price impact"].
- **Funding and borrowing rates:** `/markets/info` and `/markets/tickers`
  (`fundingRateLong/Short`, `borrowingRateLong/Short`, `netRateLong/Short`,
  30-decimal, per-hour [VERIFY the unit; the `/pairs` feed states
  `funding_rate` in "percent per hour, positive when longs pay"]). History is in
  GraphQL `fundingRateSnapshots` and `borrowingRateSnapshots` (hourly) and in
  GMX API `GET /rates?period=` (`ratesSnapshots[]`). Funding is adaptive
  (velocity-based `savedFundingFactorPerSecond`), not an 8 h or 1 h print.
- **Fees for the paper fee model:** position fee 0.04% when the trade
  improves the OI balance, 0.06% otherwise (ETH and BTC; per market in
  `/markets/config`, 30-decimal factors), plus price impact, borrowing,
  funding, a UI fee (0 via the official UI), a referral discount
  (`traderDiscountAmount`) and a keeper execution fee in ETH (gas; not in USD
  PnL). A flat 6 bps taker equivalent is a reasonable `fee_rate_bps`.
- **Daily closes:** `GET /prices/ohlcv?symbol=ETH&timeframe=1d&limit=1000`
  (1,000 daily bars, decimal strings, ms timestamps; both `ETH` and the
  market name work) and Oracle `GET /prices/candles?tokenSymbol=ETH&period=1d`.

## 5. Address and subaccount model

- EVM addresses, `0x` + 40 hex, so `watchlist.normalize_address` and
  `LeaderboardEntry.address` work unchanged (store lowercase). **New:** queries
  to the GraphQL need the EIP-55 checksum (`eth_utils.to_checksum_address`
  or a 20-line keccak helper; keccak needs `pycryptodome` or `eth-hash`
  [VERIFY what is already in the lockfile]). The REST API accepts lowercase.
- **Watched key = the wallet address (the `account`).** GMX "subaccounts" are
  delegated *signers* for one-click trading (`SubaccountRouter`,
  `MultichainSubaccountRouter`); positions stay on the main account, so no
  master/sub mapping is needed. The trade action's `account` is always the
  owner. Smart wallets (Safe, Coinbase Smart Wallet) are accounts too.
  They cannot sign Koine's EIP-191 opt-out, the same gap as Hyperliquid.
- **Chain is part of identity.** One address has independent histories on
  Arbitrum, Avalanche and MegaETH. Either one Koine venue per chain
  (`gmx_arbitrum`) or `venue = "gmx"` with chain as `env` / `account_ref`.
  `watches` today key on (venue, address) [VERIFY the exact unique
  constraint], so chain must fit there.
- Hedged positions: one account can hold long and short on the same market
  at once, and the same direction with two collateral tokens. A position is
  (market, collateral token, side). Hyperliquid nets one position per coin.
- Ownership proof for opt-out: the EIP-191 claim works as-is for EOAs.

## 7. Streaming

- **No public user-fills websocket.** No WS endpoint is documented for the GMX
  API, Oracle API or GraphQL, and the squid has no subscriptions (introspected
  `subscriptionType: null`).
- Options: (a) poll — the squid lags about 1 s and `GET /trades?address=&since=`
  is cheap. That fits `stream.py`'s nudge mode, or a fast poll for tailed
  accounts only. (b) An `eth_subscribe` logs feed on the GMX `EventEmitter`
  contract filtered by `EventLog1`/`EventLog2` topic = account (GMX emits
  `topic1 = account` for order and position events [VERIFY]). This needs an
  Arbitrum websocket RPC provider (Alchemy, QuickNode, Infura; public
  `arb1.arbitrum.io/rpc` is HTTP only [VERIFY]), and it would be Koine's first
  RPC dependency. Recommendation: polling for v1, no RPC.

(privacy of profiling third-party addresses; a US company paper-copying a
venue that excludes US persons). One addition: GMX lists TradFi perps on
US equities (SPY, QQQ, SPCX). Showing paper copies of those to US users is
a securities-adjacent display [VERIFY with counsel; option to exclude those
markets from paper copy].

## 9. Contract v2 fit vs Hyperliquid

| Need | Hyperliquid | GMX v2 | Fit |
|---|---|---|---|
| Fills, stable id | `tid`, 10k most recent | `txHash:logIndex`, full history since 2023-07 | Better |
| Fee per fill | `fee`, `feeToken` | position, borrowing, funding and liquidation fees in collateral token; impact in USD | Map to several legs |
| Funding | `userFunding` hourly events | settled at position change and claimables; no periodic events | Different; accrual becomes pending, not ledger |
| Deposits/withdrawals | `userNonFundingLedgerUpdates` | wallet mode: none (collateral per order); GMX Account: multichain events | **New model** |
| Account value | `accountValue` | sum of position `netValue` + claimables (+ GMX Account balance, no endpoint) | Synthetic |
| Positions | one per coin | per (market, collateral, side); hedging allowed | New instrument key |
| Instruments | `meta` szDecimals | markets + tokens, no tick/lot, 30-dec prices | Nominal tick/step |
| Quote | L2 book bid/ask | oracle min/max + price impact | Approximate |
| Leaderboard | one JSON, all windows | GraphQL per period, PnL/bps/volume/maxCapital, no account value | Good |
| Address | lowercase 0x | 0x, checksummed for GraphQL; per chain | Small helper + chain dimension |
| Stream | WS `userFills` (10 users/IP) | none; poll or RPC logs | Poll |
| Geoblock | none on API | none | Same |

**New shared work this forces:**
1. **A GraphQL client** (`httpx` POST plus keyset paging and size-limit
   handling) in the connector, plus a REST fallback for the GMX API with
   time-window paging (the offset cap). The throttle hook gets a new egress
   budget (GMX API and squid separately, conservative because the limits are
   unknown).
2. **30-decimal fixed point.** `money.to_micros` and `to_atoms` parse decimal
   strings; GMX gives raw scaled integers. A `gmx_units` helper turns
   integer/10^30 and price × 10^(decimals−30) into decimal strings exactly
   (Decimal or integer division with an explicit rounding rule). It needs
   hand-computed unit tests (invariant 1).
3. **Account with no balance:** methodology and `valuation.py` support for an
   account whose equity is the sum of positions, and whose external flows are
   collateral posted and paid out, with flat periods (equity 0) skipped in
   TWR. Also per-token claimable balances. This is the biggest item and also
   applies to any wallet-collateral perp DEX [VERIFY whether Drift or Lighter
   share it].
4. **Position-scoped instruments:** instrument id = market address (plus
   collateral token and side for the position), with symbol only for display.
   Signals and paper sizing must handle a creator who is long and short at once.
5. **Chain dimension:** a venue per chain or a chain field on watches,
   leaderboard snapshots and accounts. Start with `gmx_arbitrum` only.
6. **EIP-55 checksum** helper (keccak). No new chain RPC for v1.
7. **Borrowing fee** as a paper lifecycle charge (like funding; per hour from
   `borrowingRate*`), and a price-impact-aware or documented-optimistic paper
   fill.

Not needed: RPC provider, on-chain event indexing, non-0x addresses,
credentials.

## 10. Effort and risks

Effort **L**: connector (fills, claims, position changes, positions,
leaderboard, market data) about M; the no-balance valuation and methodology
work, instrument keying and the 30-decimal layer push it to L. Arbitrum only;
Avalanche is then an env flip plus fixtures.

Risks:
- Equity/TWR for wallet-collateral accounts is new methodology. Getting it wrong
  publishes misleading returns (even privately). Make it explicit and tested.
- Payout per decrease (the second output token) is not directly exposed
  [VERIFY]; derived payouts may drift from on-chain truth. Reconcile on
  position collateral and claimables only.
- Undocumented rate limits on a free hosted squid; heavy watch polling could
  be throttled or blocked without notice. Prefer the GMX API for
  per-address polling and cache leaderboard pulls (the `watch_discover` job
  already does).
- Schema churn: the GraphQL changelog shows breaking changes (e.g. 2026-02-24
  `Transaction` entity removed, sort keys renamed, backward-compatible
  endpoint for a week). Pin queries in fixtures and add a schema smoke check.
- REST `/trades` offset cap at 10,000 (confirmed); time-window paging required.
- Case-sensitive GraphQL account filter (confirmed); a lowercase query
  silently returns nothing, which would look like an empty history.
- US-person exclusion in the Interface terms (same as Hyperliquid); TradFi
  equity perps add a securities-adjacent angle.
- Multi-chain identity: the same address on Avalanche is a different track
  record; mixing them would be wrong.
- No public websocket; latency of paper copies equals the poll interval.
